# بک‌فایر 🔥

**بک‌فایر** یک تونل معکوس (Reverse Tunnel) پرسرعت است که کاملاً با **Go** نوشته
شده و برای ست‌آپ سرور ایران ⇄ خارج طراحی شده. یک **باینری واحد** با یک منوی
تعاملی است — تونل‌هایت را بدون ویرایش دستی فایل کانفیگ یا نوشتن یونیت systemd
می‌سازی و مدیریت می‌کنی.

> 📖 English guide: **[README.md](README.md)**

---

## معماری

کاربر به یک **پورت منتشرشده** روی سرور نمایان (VPS ایران) وصل می‌شود؛ انجین آن را
از طریق **یک لینک ترنسپورت مالتی‌پلکس‌شده** به کلاینت خارج می‌برد و کلاینت آن را
به **سرویس واقعی** می‌رساند.

```
   کاربر ──▶ :443 (سرور نمایان) ══ ترنسپورت+ماکس ══▶ کلاینت خارج ──▶ 127.0.0.1:443
                [ نقش سرور ]                            [ نقش کلاینت ]
```

خودِ تونل همیشه **توسط کلاینت** برقرار می‌شود (خارج → ایران)، پس سمت خارج نیازی
به پورت ورودی باز ندارد. هر اتصالِ forward‌شده به‌صورت یک استریمِ مستقل و
کنترل‌جریان‌دار روی یک اتصال فیزیکی واحد جابه‌جا می‌شود.

---

## چرا بک‌فایر؟

- **نُه ترنسپورت:** TCP خام، TCP مالتی‌پلکس، حالت stealth بدون اثرانگشت، UDP،
  UDP+KCP با تصحیح خطا، و WebSocket روی HTTP یا TLS — هر کدام در دو حالتِ pool و
  mux. عوض‌کردنشان فقط یک کلمه است.
- **مالتی‌پلکس استریم:** همه‌ی اتصال‌ها روی یک لینک با
  [smux](https://github.com/xtaci/smux) و کنترل‌جریانِ هر استریم — بدون طوفانِ
  اتصال و بدون هزینه‌ی هندشیک به‌ازای هر اتصال.
- **کانکشن پول گرم:** ترنسپورت‌های غیرمالتی‌پلکس، لینک‌ها را از قبل برقرار و
  احرازهویت‌شده نگه می‌دارند، پس هیچ کاربری روی مسیر بین‌قاره‌ای منتظرِ dial و
  هندشیک نمی‌ماند.
- **هندشیک احرازهویت‌شده و مقاوم در برابر replay:** دو طرف با یک توکن مشترک و
  چالش/پاسخ HMAC-SHA256 همدیگر را تایید می‌کنند؛ توکن حتی روی لینک `tcp` ساده هم
  از روی سیم عبور نمی‌کند. سرور تا وقتی طرفِ مقابل ثابت نکند پروتکل را می‌شناسد
  هیچ بایتی نمی‌فرستد، پس یک پورت‌اسکنر چیزی دستگیرش نمی‌شود.
- **کلاینتِ خودترمیم:** لینکِ قطع‌شده با backoff نمایی و jitter کامل دوباره برقرار
  می‌شود، پس تونل بعد از هر قطعی خودش برمی‌گردد.
- **دو خانواده‌ی تونل:** BackPack ترافیک TCP را روی نُه ترنسپورت forward می‌کند؛
  Backhaul یک تونلِ لایه‌۳ روی TUN است که به شکل ICMP/GRE/IPIP/VRRP در می‌آید و
  می‌تواند source IP را جعل کند — برای سخت‌ترین مسیرهای فیلترشده.
- **پنل وب و ربات تلگرام:** یک داشبورد مرورگری خودبسنده با گیج‌های زنده و نمودار
  ترافیک هر تونل، و رباتی که وضعیت را گزارش می‌دهد، بکاپ می‌فرستد و وقتی چیزی از
  آستانه رد شد خبرت می‌کند.
- **بهره‌برداری بدون دردسر:** منو کانفیگ را می‌نویسد، یونیت systemd (با
  `Restart=always`) را می‌سازد، فعال و اجرا می‌کند. به‌صورت پیش‌فرض مقاوم در برابر
  ریبوت.
- **کوچک و قابل‌بازبینی:** چند پکیجِ متمرکز، بدون درختِ وابستگیِ بزرگ.

## شروع سریع

روی VPS، به‌عنوان root:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/thenawid/backfire/main/install.sh)
```

نصب‌کننده باینری را می‌سازد، در `/usr/local/bin/backfire` نصب می‌کند و منو را باز
می‌کند. هر وقت خواستی دوباره باز کن:

```bash
sudo backfire
```

### ۱. روی سرور نمایان (ایران)

`backfire` → **Create server tunnel**. یک پورت listen، یک ترنسپورت و forwardهایت
را وارد کن (مثلاً `443=127.0.0.1:443`). یک **توکن** چاپ می‌شود — کپی‌اش کن.

### ۲. روی سرور مبدأ (خارج)

`backfire` → **Create client tunnel**. آدرس سرور، همان ترنسپورت و توکن را وارد
کن. تمام — کلاینت وصل می‌شود و تونل بالا می‌آید. هر دو طرف بعد از ریبوت خودشان
برمی‌گردند.

## پیکربندی دستی

هر تونل یک فایل TOML در `/etc/backfire/` است که با یک یونیت systemd اجرا می‌شود.
می‌توانی دستی هم بنویسی — به [`examples/server.toml`](examples/server.toml) و
[`examples/client.toml`](examples/client.toml) نگاه کن.

```bash
backfire -c /etc/backfire/main.toml      # حالت engine (چیزی که یونیتِ تونل اجرا می‌کند)
backfire -webui                          # پنل وب
backfire -bot                            # ربات تلگرام
backfire                                 # منوی تعاملی
backfire -v                              # نسخه
```

### فرمت forward

هر ورودی به شکل `<listen>=<target>` است:

| ورودی | منتشر روی سرور | کلاینت وصل می‌شود به |
|---|---|---|
| `443=127.0.0.1:443` | `0.0.0.0:443` | `127.0.0.1:443` |
| `0.0.0.0:2222=127.0.0.1:22` | `0.0.0.0:2222` | `127.0.0.1:22` |
| `8080` | `0.0.0.0:8080` | `127.0.0.1:8080` |

## ترنسپورت‌ها

نُه اسم، ولی فقط دو بُعد. هر ترنسپورت ترکیبی است از یک **پایه** (اینکه یک استریم
خام چطور گرفته می‌شود) و یک **حالت** (اینکه اتصال‌های forward‌شده چطور آن استریم‌ها
را بین خود تقسیم می‌کنند) — به همین دلیل نُه گزینه فقط به پنج فراهم‌کننده‌ی استریم
نیاز دارد.

| ترنسپورت | پایه | حالت | رمزنگاری | کِی؟ |
|---|---|---|---|---|
| `tcp` | TCP | pool | ندارد | مسیر تمیز، کمترین سربارِ ممکن |
| `tcpmux` | TCP | mux | ندارد | اتصال همزمانِ زیاد، کمترین تعداد سوکت |
| `stealth` | TCP | mux | **دارد** (AES-256-GCM) | DPI دارد ترافیکت را انگشت‌نگاری می‌کند |
| `udp` | UDP | mux | ندارد | TCP روی مسیر throttle یا بسته شده |
| `kcp` | UDP | mux | **دارد** (AES-256) | مسیرِ پرافت یا عمداً تخریب‌شده |
| `ws` | WebSocket | pool | ندارد | یک CDN یا پروکسی لایه۷ جلوی مسیر است |
| `wsmux` | WebSocket | mux | ندارد | مثل `ws`، با اتصال‌های زیاد |
| `wss` | WebSocket/TLS | pool | **دارد** (TLS) | هم رمزنگاری، هم سازگاری با CDN |
| `wssmux` | WebSocket/TLS | mux | **دارد** (TLS) | مثل `wss`، با اتصال‌های زیاد |

### تفاوت mux و pool

**`mux`** همه‌ی اتصال‌ها را روی یک لینک فیزیکی، هر کدام به‌عنوان یک استریمِ مستقل با
کنترل‌جریان، جابه‌جا می‌کند. یک سوکت، بدون هزینه‌ی راه‌اندازی برای هر اتصال. در عوض
همه‌ی استریم‌ها سرنوشت و پنجره‌ی congestion یک لینک را شریک می‌شوند.

**`pool`** به هر اتصال یک لینکِ اختصاصی می‌دهد که از مجموعه‌ای برداشته می‌شود که
کلاینت از قبل برقرار کرده و هندشیکش را هم انجام داده. هیچ‌چیز روی مسیرِ حساس منتظرِ
یک رفت‌وبرگشت نمی‌ماند و یک اتصالِ گیرکرده روی بقیه اثر نمی‌گذارد. هزینه‌اش سوکتِ
بیشتر است. با `[server.pool] size` تنظیمش کن.

### نکته‌های چند ترنسپورت خاص

**`stealth`** یک لینک TCP را در یک لایه‌ی رکوردِ رمزشده می‌پیچد که کلیدش از توکن
مشتق می‌شود. برخلاف TLS هیچ هندشیکی برای انگشت‌نگاری، هیچ گواهی، هیچ مذاکره‌ی نسخه و
هیچ هدر ثابتی ندارد — تنها بخشِ رمزنشده، ۳۲ بایت salt تصادفی از هر طرف است و بعد از
آن هر رکورد از بایتِ تصادفی قابل‌تشخیص نیست. DPI چیزی برای تطبیق ندارد.

**`udp` در مقابل `kcp`** — لینکِ تونل باید یک استریمِ قابل‌اعتماد و مرتب باشد تا
بتواند هندشیک و مالتی‌پلکسر را حمل کند، و UDP خام این نیست. هر دو ترنسپورت از
پروتکل KCP روی دیتاگرام‌های UDP استفاده می‌کنند تا این را فراهم کنند. `udp` آن را
لخت اجرا می‌کند: سبک‌ترین راه برای رسیدن به یک استریم قابل‌اعتماد روی UDP. `kcp`
علاوه بر آن **تصحیح خطای پیشرو** با Reed-Solomon (پیش‌فرض ۱۰ داده : ۳ توازن، پس
افتِ متوسط بدون انتظار برای بازارسال ترمیم می‌شود) و **AES-256** با کلیدِ مشتق از
توکن را اضافه می‌کند. دو طرف باید روی `mtu` و نسبتِ shard توافق داشته باشند. هر دو
سرویس‌های **TCP** را forward می‌کنند؛ forward کردنِ سرویسِ UDP در نقشه‌ی راه است.

**`wss` / `wssmux`** — خالی‌گذاشتنِ `tls_cert`/`tls_key` یک گواهی self-signed در
حافظه می‌سازد. این اشکالی ندارد، چون دو طرف با **توکن** همدیگر را تایید می‌کنند نه با
زنجیره‌ی گواهی. اگر دامنه‌ی مشخصی را terminate می‌کنی به یک گواهی واقعی اشاره بده و
روی کلاینت `tls_verify = true` بگذار.

## پنل وب

`sudo backfire` ← **Web panel** ← *Set up*. پورت را می‌پرسد، یک کد ورود **پیشنهاد
می‌دهد** (با زدن Enter همان ثبت می‌شود) و می‌پرسد پنل فقط-نمایشی باشد یا نه. بعد
یونیت را می‌نویسد و اجرا می‌کند.

پنل، CPU / حافظه / دیسک / swap و پهنای‌باند سرور را نشان می‌دهد، به‌علاوه‌ی یک کارت
برای هر تونل با ترنسپورت، پورت‌ها، پینگ، ترافیک زنده، نمودار throughput و لاگ‌های
journal. هر ۳ ثانیه تازه می‌شود.

پنل یک فایل HTML امبدشده است و **هیچ فایل بیرونی** ندارد — نه CDN، نه فونت، نه
اسکریپتی که باید دانلود شود — پس روی سروری که به اینترنت بیرونی دسترسی ندارد هم
کار می‌کند.

> کد ورود تنها چیزی است که از پنل محافظت می‌کند. کد بلند بگذار، و ترجیحاً به‌جای
> باز کردن پورتش روی اینترنت، از تونل SSH یا VPN به آن وصل شو.

## ربات تلگرام

`sudo backfire` ← **Telegram bot** ← *Set up*. توکن را از
[@BotFather](https://t.me/BotFather) و آی‌دی عددی‌ات را از
[@userinfobot](https://t.me/userinfobot) بگیر.

| دستور | چه می‌کند |
|---|---|
| `/status` | هر تونل: وضعیت، پورت‌ها، ترافیک، پینگ |
| `/system` | پردازنده، حافظه، دیسک، آپ‌تایم |
| `/backup` | همه‌ی کانفیگ‌ها و تنظیمات را به‌صورت `.tar.gz` می‌فرستد |
| `/alerts` | آستانه‌های هشدار فعلی |
| `/webui` | لینک پنل و کد ورود |
| `/support` | لینک‌های پروژه |

هر پاسخ یک کیبورد شیشه‌ای دارد و زدن هر دکمه **همان پیام را ویرایش می‌کند** — پس
چت به‌جای یک لیست طولانی، یک پنلِ زنده باقی می‌ماند.

با فعال‌بودن هشدارها، ربات وقتی CPU، حافظه یا دیسک از آستانه رد شود خبرت می‌کند —
یک‌بار موقع رد شدن و یک‌بار موقع برگشتن به حالت عادی، نه در هر بررسی — و هر وقت
تونلی طرفِ مقابلش را از دست بدهد یا دوباره وصل شود.

**ربات فقط به آی‌دی‌هایی که تعیین کرده‌ای جواب می‌دهد.** بقیه رد می‌شوند و فقط آی‌دی
خودشان به آن‌ها گفته می‌شود. اگر لیست ادمین خالی باشد ربات اصلاً بالا نمی‌آید.

> `/backup` توکن‌های واقعی تونل را از طریق تلگرام می‌فرستد. کارکردِ همین دستور
> است، ولی با فایلِ حاصل مثل یک راز رفتار کن.

## Backhaul — تونل‌های لایه‌۳

کنار نُه ترنسپورتِ BackPack (که TCP را forward می‌کنند)، backfire یک خانواده‌ی
دوم دارد: **Backhaul**، یک تونلِ نقطه‌به‌نقطه‌ی لایه‌۳ روی یک دستگاه TUN. جایی که
BackPack مخفی می‌کند «چطور» یک اتصال حمل می‌شود، Backhaul ترافیک را به شکلِ **یک
پروتکل IP کاملاً دیگر** در می‌آورد و می‌تواند آدرس مبدأ را جعل کند.

هر طرف یک رابط TUN و یک آدرسِ خصوصیِ نقطه‌به‌نقطه می‌گیرد؛ هر بسته‌ی IP با
AES-256-GCM (کلید مشتق از توکن) رمز می‌شود و داخلِ حاملِ انتخابی فرستاده می‌شود:

| حامل | شبیهِ | پورت | اسپوف |
|---|---|---|---|
| `udp` | ترافیک UDP | دارد | ندارد |
| `tcp` | یک استریم TCP | دارد | ندارد |
| `icmp` | پینگ (ICMP echo) | ندارد | دارد |
| `ipip` | IP-in-IP (پروتکل ۴) | ندارد | دارد |
| `gre` | تونل GRE (پروتکل ۴۷) | ندارد | دارد |
| `vrrp` | VRRP (پروتکل ۱۱۲) | ندارد | دارد |
| `bip` | آزمایشی (پروتکل ۲۵۳) | ندارد | دارد |

**اسپوف IP** (حامل‌های raw) بسته‌های حامل را با آدرس مبدأ جعلی می‌فرستد تا مبدأ
واقعی روی سیم دیده نشود. برای مبدأ تصادفی که هر ری‌استارت عوض شود، آن را خالی بگذار.

Backhaul به **root** نیاز دارد (CAP_NET_ADMIN برای TUN و CAP_NET_RAW برای
حامل‌های raw). رابط مستقیم با ioctl ساخته و آدرس‌دهی می‌شود، بدون وابستگی به
`iproute2`. به [`examples/backhaul.toml`](examples/backhaul.toml) نگاه کن یا با
`sudo backfire` ← *ساخت تونل* ← **Backhaul** بساز.

> حامل‌های raw فقط *شماره‌ی* پروتکل را برای استتار استفاده می‌کنند، نه فرمتِ کاملِ
> هدرِ آن پروتکل را. forward کردنِ *سرویسِ* UDP هنوز در نقشه‌ی راه است.

## نکات امنیتی

- توکن کلِ مرزِ امنیت است — یک مقدار تصادفیِ بلند بساز (گزینه‌ی ۷ منو) و فایل‌های
  کانفیگ را `0600` نگه‌دار (نصب‌کننده این کار را برایت انجام می‌دهد).
- روی کلاینت می‌توانی `allowed_targets` را ست کنی تا دقیقاً مشخص شود سرور اجازه‌ی
  درخواست dial به کدام `host:port` را دارد.
- فایل‌های کانفیگ توکن واقعی دارند — هیچ‌وقت در گیت قرارشان نده (الگوهای
  `.gitignore` هم آن‌ها را نادیده می‌گیرند).

## ساخت و تست از سورس

```bash
git clone https://github.com/thenawid/backfire.git
cd backfire
make build      # -> ./backfire
make test       # تست‌های واحد + تونلِ سرتاسریِ درون‌فرایندی روی tcp/ws/wss
make vet
```

تستِ سرتاسری در [`internal/e2e`](internal/e2e) یک سرور+کلاینتِ واقعی را روی
loopback برای هر ترنسپورت بالا می‌آورد و رفت‌وبرگشتِ بایت را از کلِ استک (هندشیک،
ماکس، فریمینگ، forwarding) بررسی می‌کند.

## نقشه‌ی راه

- forward کردنِ *سرویس‌های* UDP (ترنسپورت‌های udp/kcp فعلاً سرویس TCP را حمل می‌کنند)
- ترنسپورت QUIC
- HTTPS برای پنل، و بازگردانی از بکاپ در ربات
- باینری‌های آماده‌ی release با نصبِ تاییدشده با checksum
